# Requirements Document

## Introduction

This document defines the requirements for optimizing the Mawgood e-commerce platform for production deployment on Hostinger servers. The system consists of four applications: Backend (Medusa v2 API), Admin Panel (React/Vite), Vendor Panel (React/Vite), and Storefront (Next.js). The optimization focuses on image handling, data stability, performance, production-ready packages, server configuration, and GitHub deployment workflow.

## Glossary

- **Backend**: The Medusa v2 Node.js/Express API server running on port 9000
- **Admin_Panel**: The React/Vite admin dashboard application running on port 5173
- **Vendor_Panel**: The React/Vite vendor management application running on port 5174
- **Storefront**: The Next.js customer-facing e-commerce application running on port 3000
- **Static_Image_Server**: The Express middleware serving static images from backend/static directory
- **Production_Environment**: The Hostinger server environment where the application will be deployed
- **Image_Asset**: Any image file stored in backend/static/extracted-images directory
- **Product_Data**: Product information including variants, prices, and metadata stored in PostgreSQL
- **Build_Artifact**: Compiled production-ready code generated by build processes
- **Performance_Metric**: Measurable indicators including load time, response time, and resource usage
- **Deployment_Pipeline**: The automated process from GitHub push to production server deployment
- **Error_Boundary**: React component that catches JavaScript errors in component tree
- **Lazy_Loading**: Technique to defer loading of non-critical resources until needed
- **Asset_Optimization**: Process of compressing and optimizing images, fonts, and other static files
- **Cache_Strategy**: Configuration for browser and server-side caching of static resources
- **Health_Check**: Endpoint or mechanism to verify application availability and status
- **Graceful_Shutdown**: Process of cleanly stopping services without data loss or corruption
- **Environment_Variable**: Configuration value stored outside code for different deployment environments
- **Database_Connection_Pool**: Managed set of reusable database connections
- **Static_Asset_CDN**: Content delivery network for serving static files with low latency
- **Bundle_Size**: Total size of JavaScript and CSS files sent to browser
- **Tree_Shaking**: Removal of unused code from production bundles
- **Code_Splitting**: Breaking application into smaller chunks loaded on demand
- **Compression_Middleware**: Server middleware that compresses HTTP responses
- **Rate_Limiting**: Mechanism to limit number of requests from single source
- **CORS_Policy**: Cross-Origin Resource Sharing configuration for API access
- **SSL_Certificate**: Security certificate for HTTPS encryption
- **Process_Manager**: Tool (PM2) that manages and monitors Node.js processes
- **Memory_Limit**: Maximum RAM allocation for each application process
- **Log_Rotation**: Automatic archiving and cleanup of application logs
- **Fallback_Image**: Default placeholder image shown when actual image fails to load
- **Image_Format**: File format for images (JPEG, PNG, WebP, AVIF)
- **Responsive_Image**: Image that adapts to different screen sizes and resolutions
- **Database_Migration**: Versioned changes to database schema
- **Seed_Data**: Initial data loaded into database for production
- **API_Timeout**: Maximum time allowed for API request to complete
- **Retry_Logic**: Automatic retry mechanism for failed operations
- **Circuit_Breaker**: Pattern to prevent cascading failures in distributed systems
- **Monitoring_Service**: External service tracking application health and performance
- **Backup_Strategy**: Automated process for backing up database and critical files
- **Rollback_Procedure**: Process to revert to previous working version if deployment fails

## Requirements

### Requirement 1: Image Asset Reliability

**User Story:** As a customer, I want all product images to load correctly without errors, so that I can view products properly before purchasing.

#### Acceptance Criteria

1. THE Static_Image_Server SHALL serve all Image_Assets from backend/static/extracted-images directory
2. WHEN an Image_Asset request is received, THE Static_Image_Server SHALL respond within 500ms
3. IF an Image_Asset does not exist, THEN THE Static_Image_Server SHALL return a Fallback_Image with HTTP 200 status
4. THE Storefront SHALL implement Lazy_Loading for all Image_Assets below the fold
5. THE Admin_Panel SHALL implement Lazy_Loading for all Image_Assets in product lists
6. THE Vendor_Panel SHALL implement Lazy_Loading for all Image_Assets in product lists
7. WHEN an Image_Asset fails to load, THE Storefront SHALL display a Fallback_Image without breaking the layout
8. WHEN an Image_Asset fails to load, THE Admin_Panel SHALL display a Fallback_Image without breaking the layout
9. WHEN an Image_Asset fails to load, THE Vendor_Panel SHALL display a Fallback_Image without breaking the layout
10. THE Backend SHALL validate Image_Asset file extensions are in allowed list (jpg, jpeg, png, webp, avif, gif)
11. THE Backend SHALL reject Image_Asset uploads exceeding 5MB in size
12. FOR ALL Image_Assets, THE Asset_Optimization process SHALL compress images to reduce file size by at least 30% without visible quality loss

### Requirement 2: Modern Image Format Support

**User Story:** As a developer, I want to serve modern image formats with fallbacks, so that the application loads faster on modern browsers while maintaining compatibility.

#### Acceptance Criteria

1. THE Asset_Optimization process SHALL convert JPEG and PNG images to WebP format
2. THE Asset_Optimization process SHALL convert JPEG and PNG images to AVIF format where supported
3. THE Storefront SHALL serve AVIF images to browsers that support AVIF
4. THE Storefront SHALL serve WebP images to browsers that support WebP but not AVIF
5. THE Storefront SHALL serve original JPEG or PNG images to browsers that support neither WebP nor AVIF
6. THE Admin_Panel SHALL serve WebP images with JPEG/PNG fallbacks
7. THE Vendor_Panel SHALL serve WebP images with JPEG/PNG fallbacks
8. THE Backend SHALL store original images and generated WebP/AVIF variants
9. WHEN generating image variants, THE Asset_Optimization process SHALL preserve original aspect ratio
10. THE Asset_Optimization process SHALL generate responsive image sizes (thumbnail, small, medium, large)

### Requirement 3: Product Data Stability

**User Story:** As a store administrator, I want product data to remain stable and consistent, so that customers see accurate information without crashes or errors.

#### Acceptance Criteria

1. THE Backend SHALL validate all Product_Data before saving to database
2. WHEN Product_Data contains invalid price values, THE Backend SHALL reject the request with descriptive error message
3. WHEN Product_Data contains missing required fields, THE Backend SHALL reject the request with descriptive error message
4. THE Backend SHALL enforce price values are positive integers in cents (e.g., 29000 for 290 EGP)
5. THE Backend SHALL enforce product handles are unique and URL-safe
6. THE Storefront SHALL implement Error_Boundary components around product listing and detail pages
7. THE Admin_Panel SHALL implement Error_Boundary components around product management pages
8. THE Vendor_Panel SHALL implement Error_Boundary components around product management pages
9. WHEN Product_Data query fails, THE Storefront SHALL display user-friendly error message without crashing
10. WHEN Product_Data query fails, THE Admin_Panel SHALL display user-friendly error message without crashing
11. WHEN Product_Data query fails, THE Vendor_Panel SHALL display user-friendly error message without crashing
12. THE Backend SHALL implement Database_Connection_Pool with minimum 5 and maximum 20 connections
13. WHEN database connection is lost, THE Backend SHALL attempt reconnection with exponential backoff up to 5 times
14. THE Backend SHALL log all Product_Data validation errors with request context for debugging

### Requirement 4: Application Performance Optimization

**User Story:** As a customer, I want the website to load quickly and respond smoothly, so that I can browse and purchase products efficiently.

#### Acceptance Criteria

1. THE Storefront SHALL achieve First Contentful Paint (FCP) under 1.5 seconds on 3G connection
2. THE Storefront SHALL achieve Largest Contentful Paint (LCP) under 2.5 seconds on 3G connection
3. THE Storefront SHALL achieve Time to Interactive (TTI) under 3.5 seconds on 3G connection
4. THE Storefront SHALL achieve Cumulative Layout Shift (CLS) score below 0.1
5. THE Admin_Panel SHALL load initial page within 2 seconds on broadband connection
6. THE Vendor_Panel SHALL load initial page within 2 seconds on broadband connection
7. THE Storefront SHALL implement Code_Splitting for route-based chunks
8. THE Admin_Panel SHALL implement Code_Splitting for route-based chunks
9. THE Vendor_Panel SHALL implement Code_Splitting for route-based chunks
10. THE Storefront SHALL reduce total Bundle_Size to under 300KB for initial load (gzipped)
11. THE Admin_Panel SHALL reduce total Bundle_Size to under 400KB for initial load (gzipped)
12. THE Vendor_Panel SHALL reduce total Bundle_Size to under 400KB for initial load (gzipped)
13. THE Backend SHALL implement Compression_Middleware for all HTTP responses
14. THE Backend SHALL enable gzip compression with compression level 6
15. THE Backend SHALL enable Brotli compression for static assets where supported
16. THE Storefront SHALL implement Cache_Strategy with 1 year cache for static assets
17. THE Admin_Panel SHALL implement Cache_Strategy with 1 year cache for static assets
18. THE Vendor_Panel SHALL implement Cache_Strategy with 1 year cache for static assets
19. THE Backend SHALL set Cache-Control headers for Image_Assets with max-age of 31536000 seconds
20. THE Storefront SHALL prefetch critical resources for next likely navigation
21. THE Storefront SHALL preload critical fonts and above-the-fold images
22. THE Backend SHALL implement API_Timeout of 30 seconds for all endpoints
23. THE Backend SHALL implement database query timeout of 10 seconds
24. THE Storefront SHALL implement service worker for offline capability and faster repeat visits

### Requirement 5: Production Package Configuration

**User Story:** As a developer, I want all applications to use production-optimized packages and configurations, so that the system runs efficiently and securely in production.

#### Acceptance Criteria

1. THE Backend SHALL use NODE_ENV=production environment variable
2. THE Storefront SHALL use NODE_ENV=production environment variable
3. THE Admin_Panel SHALL use NODE_ENV=production environment variable
4. THE Vendor_Panel SHALL use NODE_ENV=production environment variable
5. THE Backend SHALL install compression package for HTTP response compression
6. THE Backend SHALL install helmet package for security headers
7. THE Backend SHALL install express-rate-limit package for Rate_Limiting
8. THE Backend SHALL install pm2 package globally as Process_Manager
9. THE Storefront SHALL enable Next.js production optimizations (minification, Tree_Shaking)
10. THE Admin_Panel SHALL enable Vite production optimizations (minification, Tree_Shaking)
11. THE Vendor_Panel SHALL enable Vite production optimizations (minification, Tree_Shaking)
12. THE Backend SHALL configure helmet middleware with secure defaults
13. THE Backend SHALL configure Rate_Limiting to 100 requests per 15 minutes per IP for API endpoints
14. THE Backend SHALL configure CORS_Policy to allow only Production_Environment domains
15. THE Backend SHALL disable detailed error messages in production responses
16. THE Backend SHALL enable trust proxy setting for correct client IP detection behind reverse proxy
17. THE Storefront SHALL remove all console.log statements from production build
18. THE Admin_Panel SHALL remove all console.log statements from production build
19. THE Vendor_Panel SHALL remove all console.log statements from production build
20. THE Backend SHALL install sharp package for efficient image processing
21. THE Backend SHALL configure sharp for WebP and AVIF conversion with quality 80

### Requirement 6: Server Configuration and Monitoring

**User Story:** As a system administrator, I want the server properly configured with monitoring and auto-recovery, so that the application remains available and issues are detected quickly.

#### Acceptance Criteria

1. THE Process_Manager SHALL restart any crashed application process automatically
2. THE Process_Manager SHALL limit Backend Memory_Limit to 1GB
3. THE Process_Manager SHALL limit Storefront Memory_Limit to 1GB
4. THE Process_Manager SHALL limit Admin_Panel Memory_Limit to 500MB
5. THE Process_Manager SHALL limit Vendor_Panel Memory_Limit to 500MB
6. THE Process_Manager SHALL implement Log_Rotation with maximum 10 files of 10MB each
7. THE Backend SHALL expose Health_Check endpoint at /health returning HTTP 200 when operational
8. THE Storefront SHALL expose Health_Check endpoint at /api/health returning HTTP 200 when operational
9. THE Backend SHALL implement Graceful_Shutdown handling SIGTERM and SIGINT signals
10. THE Storefront SHALL implement Graceful_Shutdown handling SIGTERM and SIGINT signals
11. THE Backend SHALL close Database_Connection_Pool during Graceful_Shutdown
12. THE Backend SHALL wait up to 30 seconds for in-flight requests to complete during Graceful_Shutdown
13. THE Process_Manager SHALL log application start, stop, and restart events
14. THE Backend SHALL log all unhandled errors with stack traces
15. THE Backend SHALL log all API requests with method, path, status code, and response time
16. THE Backend SHALL implement structured logging in JSON format for production
17. THE Production_Environment SHALL configure reverse proxy (Nginx/Apache) to forward requests to applications
18. THE Production_Environment SHALL configure SSL_Certificate for HTTPS on all domains
19. THE Production_Environment SHALL redirect all HTTP traffic to HTTPS
20. THE Production_Environment SHALL configure firewall to allow only ports 80, 443, and SSH
21. THE Backend SHALL validate all Environment_Variable values on startup and fail fast if invalid
22. THE Production_Environment SHALL set up automated database backups daily at 2 AM UTC
23. THE Production_Environment SHALL retain database backups for 30 days
24. THE Process_Manager SHALL send alerts when application restarts exceed 3 times in 1 hour

### Requirement 7: GitHub Deployment Workflow

**User Story:** As a developer, I want a streamlined deployment process from GitHub to production, so that updates can be deployed safely and quickly.

#### Acceptance Criteria

1. THE Deployment_Pipeline SHALL trigger on push to main branch
2. THE Deployment_Pipeline SHALL run all tests before deployment
3. THE Deployment_Pipeline SHALL build all applications before deployment
4. THE Deployment_Pipeline SHALL fail deployment if any test fails
5. THE Deployment_Pipeline SHALL fail deployment if any build fails
6. THE Deployment_Pipeline SHALL create Build_Artifact for Backend
7. THE Deployment_Pipeline SHALL create Build_Artifact for Storefront
8. THE Deployment_Pipeline SHALL create Build_Artifact for Admin_Panel
9. THE Deployment_Pipeline SHALL create Build_Artifact for Vendor_Panel
10. THE Deployment_Pipeline SHALL transfer Build_Artifacts to Production_Environment via SSH
11. THE Deployment_Pipeline SHALL run Database_Migration on Production_Environment before starting applications
12. THE Deployment_Pipeline SHALL backup database before running Database_Migration
13. THE Deployment_Pipeline SHALL restart applications using Process_Manager after successful deployment
14. THE Deployment_Pipeline SHALL verify Health_Check endpoints return success after deployment
15. IF Health_Check fails after deployment, THEN THE Deployment_Pipeline SHALL execute Rollback_Procedure
16. THE Rollback_Procedure SHALL restore previous Build_Artifacts
17. THE Rollback_Procedure SHALL restore database from backup if Database_Migration was run
18. THE Rollback_Procedure SHALL restart applications using Process_Manager
19. THE Deployment_Pipeline SHALL send notification on successful deployment
20. THE Deployment_Pipeline SHALL send notification on failed deployment with error details
21. THE Deployment_Pipeline SHALL maintain deployment history with timestamps and commit hashes
22. THE Deployment_Pipeline SHALL support manual rollback to any previous deployment

### Requirement 8: Error Handling and Resilience

**User Story:** As a customer, I want the application to handle errors gracefully without showing technical details, so that I can continue using the site even when issues occur.

#### Acceptance Criteria

1. THE Storefront SHALL display user-friendly error page for 404 errors
2. THE Storefront SHALL display user-friendly error page for 500 errors
3. THE Admin_Panel SHALL display user-friendly error page for 404 errors
4. THE Admin_Panel SHALL display user-friendly error page for 500 errors
5. THE Vendor_Panel SHALL display user-friendly error page for 404 errors
6. THE Vendor_Panel SHALL display user-friendly error page for 500 errors
7. WHEN API request fails, THE Storefront SHALL implement Retry_Logic with exponential backoff up to 3 attempts
8. WHEN API request fails, THE Admin_Panel SHALL implement Retry_Logic with exponential backoff up to 3 attempts
9. WHEN API request fails, THE Vendor_Panel SHALL implement Retry_Logic with exponential backoff up to 3 attempts
10. THE Backend SHALL implement Circuit_Breaker for external service calls
11. THE Backend SHALL open Circuit_Breaker after 5 consecutive failures
12. THE Backend SHALL attempt Circuit_Breaker reset after 60 seconds
13. WHEN Circuit_Breaker is open, THE Backend SHALL return cached response or fallback data
14. THE Backend SHALL catch all unhandled promise rejections and log them
15. THE Backend SHALL catch all uncaught exceptions and log them before graceful shutdown
16. THE Storefront SHALL implement global error boundary at root level
17. THE Admin_Panel SHALL implement global error boundary at root level
18. THE Vendor_Panel SHALL implement global error boundary at root level
19. WHEN error boundary catches error, THE application SHALL log error details to monitoring service
20. WHEN error boundary catches error, THE application SHALL display recovery options to user

### Requirement 9: Security Hardening

**User Story:** As a security administrator, I want the application to follow security best practices, so that customer data and business operations are protected.

#### Acceptance Criteria

1. THE Backend SHALL set X-Content-Type-Options header to nosniff
2. THE Backend SHALL set X-Frame-Options header to DENY
3. THE Backend SHALL set X-XSS-Protection header to 1; mode=block
4. THE Backend SHALL set Strict-Transport-Security header with max-age 31536000
5. THE Backend SHALL set Content-Security-Policy header with restrictive policy
6. THE Backend SHALL sanitize all user input before database queries
7. THE Backend SHALL use parameterized queries for all database operations
8. THE Backend SHALL validate file uploads for allowed types and sizes
9. THE Backend SHALL scan uploaded files for malware signatures
10. THE Backend SHALL store sensitive Environment_Variables in secure configuration (not in code)
11. THE Backend SHALL hash and salt all passwords using bcrypt with cost factor 12
12. THE Backend SHALL implement JWT token expiration of 24 hours
13. THE Backend SHALL implement refresh token rotation
14. THE Backend SHALL log all authentication attempts (success and failure)
15. THE Backend SHALL implement account lockout after 5 failed login attempts within 15 minutes
16. THE Backend SHALL require HTTPS for all API endpoints in production
17. THE Storefront SHALL implement CSRF protection for all form submissions
18. THE Admin_Panel SHALL implement CSRF protection for all form submissions
19. THE Vendor_Panel SHALL implement CSRF protection for all form submissions
20. THE Backend SHALL implement SQL injection prevention through ORM usage
21. THE Backend SHALL implement XSS prevention through output encoding
22. THE Production_Environment SHALL disable directory listing on web server
23. THE Production_Environment SHALL hide server version information in HTTP headers
24. THE Backend SHALL implement API key rotation mechanism for external integrations

### Requirement 10: Database Optimization

**User Story:** As a database administrator, I want the database optimized for production workload, so that queries execute quickly and the system scales efficiently.

#### Acceptance Criteria

1. THE Backend SHALL create database indexes on product.handle column
2. THE Backend SHALL create database indexes on product_variant.sku column
3. THE Backend SHALL create database indexes on price.currency_code column
4. THE Backend SHALL create database indexes on product.created_at column
5. THE Backend SHALL create composite index on (product_id, variant_id) for product_variant table
6. THE Backend SHALL configure Database_Connection_Pool with connection timeout of 30 seconds
7. THE Backend SHALL configure Database_Connection_Pool with idle timeout of 10 seconds
8. THE Backend SHALL implement query result caching for frequently accessed data
9. THE Backend SHALL cache product listings for 5 minutes
10. THE Backend SHALL cache category data for 15 minutes
11. THE Backend SHALL invalidate cache when Product_Data is updated
12. THE Backend SHALL implement database query logging for queries exceeding 1 second
13. THE Backend SHALL use database transactions for multi-step operations
14. THE Backend SHALL implement optimistic locking for concurrent updates
15. THE Backend SHALL paginate all list queries with maximum page size of 100 items
16. THE Backend SHALL use cursor-based pagination for large datasets
17. THE Backend SHALL implement read replicas for read-heavy operations if available
18. THE Backend SHALL analyze and optimize slow queries identified in logs
19. THE Backend SHALL run VACUUM ANALYZE on PostgreSQL database weekly
20. THE Backend SHALL monitor database connection pool utilization and alert if exceeds 80%

**User Story:** As a DevOps engineer, I want comprehensive monitoring and logging, so that I can quickly identify and resolve production issues.

2. THE Backend SHALL send custom metrics for API response times to Monitoring_Service
3. THE Backend SHALL send custom metrics for database query times to Monitoring_Service
4. THE Backend SHALL send custom metrics for error rates to Monitoring_Service
5. THE Backend SHALL implement distributed tracing for request flows across services
6. THE Backend SHALL assign unique request ID to each API request
7. THE Backend SHALL include request ID in all log entries for request correlation
8. THE Backend SHALL log slow API requests (exceeding 2 seconds) with full context

11. THE Backend SHALL implement alerting for memory usage exceeding 90% of Memory_Limit
12. THE Backend SHALL implement alerting for CPU usage exceeding 80% for 5 minutes
13. THE Backend SHALL implement alerting for database connection pool exhaustion
14. THE Backend SHALL implement alerting for disk space usage exceeding 85%
15. THE Monitoring_Service SHALL provide dashboard showing key Performance_Metrics
16. THE Monitoring_Service SHALL retain metrics data for 90 days
17. THE Backend SHALL implement log aggregation sending logs to centralized logging service
18. THE Backend SHALL implement log levels (error, warn, info, debug) with production using info level

20. THE Monitoring_Service SHALL provide real-time alerts via email and SMS for critical issues
